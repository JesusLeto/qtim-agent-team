# /qtim:team-lazy — лёгкий режим без warm-up

> Читает только team-lead. Канон рантайма (`Agent`/`SendMessage`/`Task*`, упразднённые `TeamCreate`/`team_name`), Decision Matrix и правила из секции «Важно» — в [`team-up.md`](team-up.md); они действуют и здесь, в частности запрос независимого оппонента от роли на money-critical гейте. Ниже — отличия lazy-режима.

## Когда

Режим **C** из Decision Matrix: несколько слоёв за один проход БЕЗ петель доводки impl↔test↔review. Средняя фича (например миграция + UI), баг-фикс на 2-3 роли, fan-out-аудит. Платишь только за реально поднятых членов.

## Как

1. **Команду НЕ прогреваешь.** Она существует неявно (сессия = одна команда). Ничего не создаёшь.
2. **Спавнишь роль в момент необходимости** через `Agent({ name, subagent_type, prompt })` — `subagent_type` и `read on spawn` бери из `.claude/team-charter.md`. Прочитай charter, если он ещё не в контексте. Если задача ссылается на фичу из `docs/features/<slug>/` — её `plan.md`/`prd.md` (fast-path-фича — единый `feature-brief.md`) являются источником scope; по завершении обнови Status артефактов, а отклонения от плана с обоснованием и всплывшие edge cases зафиксируй строкой в «Истории изменений» планового документа; служебные файлы фазы (отчёты ревью, consult-выводы, брифы проверок) — в `docs/features/<slug>/.work/` по скилу `qtim:kb-format`. Указанный пользователем утверждённый план этого репозитория и слоя — пройденный approval-гейт (условия — шаг 3 intake-protocol). До первой фазы прочитай в [`intake-protocol.md`](../reference/intake-protocol.md) шаги 3–5 и разделы «Бюджет проверки на реализации» и «Старшинство указаний и объём»: там стопы, потолок кругов и граница объёма.
3. **Каждый член** при старте читает CLAUDE.md + свою секцию charter + свои `read on spawn`, отрабатывает задачу. Промпт спавна — тот же компактный контракт, что в [`team-up.md`](team-up.md) (шаг 4), включая строку про задачи: нет `Task*` у роли (ни в наборе, ни через `ToolSearch`) — она присылает состав задачи тебе через `SendMessage`, список ведёшь ты.
4. **Следующий шаг цепочки** — `SendMessage({ to: "<name>" })` (контекст члена сохранён), а не повторный `Agent` (тот стартует с нуля).
5. **Параллельный fan-out** — несколько `Agent` одним сообщением, если единицы работы независимы.

## Критерий переключения C → D

Как только появляется **петля обратной связи** (tester нашёл баг → исполнитель правит → re-test → reviewer вернул на доработку), ты фактически в режиме **D**. Не отменяй уже поднятых — просто доспавни недостающих обычными `Agent`-вызовами (team одна на сессию, дублей не будет) и веди общий `Task*` list. Эскалация вверх дешёвая — это и есть причина начинать с lazy при сомнении.

## Anti-patterns

- Спавнить всех «на всякий случай» — это уже `/qtim:team-up`, а не lazy.
- Повторный `Agent` с тем же `name` для продолжения — теряешь контекст; используй `SendMessage`.
- Тащить orchestration-логику в промпты членов — она только у team-lead.
