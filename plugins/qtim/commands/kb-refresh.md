# /qtim:kb-refresh — актуализация базы знаний

> Читает только team-lead. Запускает пользователь: подсказка SessionStart о свежести памяти —
> справка для него, а не повод запускать самому. Канон формата — скил `qtim:kb-format` (вызови
> его до первой записи); факты и счётчики отдаёт его скрипт `kb_scan.py`, а глубину прогона,
> оценку и потолки считаешь ты по этому файлу — больше они нигде не живут. Канон рантайма —
> в [`team-up.md`](team-up.md).

Модель тратится только на сверку устаревших файлов с кодом; скан, подготовка и операции
детерминированы. **Память правится на месте** — в дереве пользователя, где её читают скан и
снимок; код базы читается по её sha, рабочее дерево пользователя для сверки не используется.
Ветку пользователя прогон не переключает, `stash`/`checkout`/`reset` не делает.

## 0. Готовность

1. `python3 --version` — нет или ниже 3.9 → стоп: «для /qtim:kb-refresh нужен python3 ≥ 3.9».
2. Скрипт — `${CLAUDE_PLUGIN_ROOT}/skills/kb-format/scripts/kb_scan.py`; файла нет —
   `.claude/skills/kb-format/scripts/kb_scan.py` (standalone); нет и его → стоп: «`kb_scan.py`
   не найден — обнови плагин qtim; в standalone — `/qtim:team-sync`». Дальше он — `<kb_scan>`,
   запуск из корня рабочего дерева пользователя.
3. `python3 <kb_scan> prepare --json` (с `--base $ARGUMENTS`, если аргумент задан). Для любого
   вывода скрипта: `schema` ≠ `kb_scan/1` → стоп «версия скрипта не совпадает с командой»;
   `scan_complete: false` → стоп с `errors[].message` и `errors[].fix`. Дальше по полям:
   - `storage.memory.present: false` → актуализировать нечего: предложи `/qtim:onboard`, стоп.
   - `lock.state: locked` и `lock.holder.run` == `resume.run` — прерванный прогон: вопрос
     «продолжить прерванный прогон (начат <lock.holder.started_at>)? Если в другой сессии сейчас
     идёт kb-refresh — ответь нет»; «да» — продолжение берёт лок
     (`snapshot --run <resume.run> --force-lock`, `before` не перезаписывается). Иначе
     `locked` — стоп и вопрос: идёт другой прогон (`lock.holder`).
   - `repo.base.ask_base: true` → вопрос о базе сейчас, до скана: без базы скана нет.
     Кандидаты — `storage.memory.refs_with_memory`; main/master не угадывай.
   - `repo.base.fetch_error` не `null` → работаешь по локальным ref'ам; первая строка отчёта —
     «база не обновлена: <ошибка>».
   - `overwrite.suspects` не пуст → стоп: покажи файлы с `reason` и `evidence` и источники
     восстановления по порядку — снимок завершённого прогона → `git log -p -- <файл>` → stash →
     транскрипты сессий проекта (последний `Write`/`Edit` файла). Варианты: восстановить /
     «диск верен, продолжить» (для `vanished` — «удалено намеренно») / только отчёт / отмена.
     «Диск верен» принимается только явным ответом пользователя, не твоим выводом. Перед
     восстановлением — снимок текущего диска (шаг 4; прогон дальше идёт с тем же `<run>`),
     затем повтори `prepare`. Пока подозрение не закрыто, доступна только глубина «только
     отчёт».
   - `storage.memory.disk_richer_than_head` — не стоп: на диске память богаче, чем в HEAD
     (незакоммиченная работа пользователя), строка-предупреждение в вопросе старта.

Id прогона `<run>` — `prepare.run.free_id` из первого `prepare`, при resume — `resume.run`.
`resume.run`, равный текущему `<run>` (прогон начат снимком перед восстановлением на этом
шаге), — не resume, а тот же прогон.

Внеочередные стопы этого шага — не точка вопросов старта: они случаются до скана.

## 1. Скан

`python3 <kb_scan> all --base <база> --json` — `validate`, `delta`, `features`, `automemory`,
`memory_words`. База — `repo.base.ref` или ответ на вопрос о базе; `<base-sha>` — её sha.
Каталог auto-memory — путь, который дословно называет блок auto-memory твоего системного
промпта: передавай его флагом `--automemory-dir` в `all`, `snapshot` и `lost`; блока нет — флаг
опусти.

`delta.ask_base: true` или у файлов `sha_state: not_ancestor` (память записана на ветке, чьих
коммитов нет в базе) → вопрос о базе, как на шаге 0, и повтор скана.

## 2. Глубина прогона

Собственный потолок ресурсов одного прогона без кругов — не режим A/B/C/D и не бюджет проверки
intake-протокола. `n` = `delta.stale_file_claims_total` — все утверждения в устаревших файлах
(`delta.files[]` со `stale: true`): устаревший файл проверяется целиком.

| Глубина | Условие | Кто работает |
|---|---|---|
| `none` | ни одного устаревшего файла | агентов 0: формат, бюджеты, архивация, auto-memory — детерминированно или отчётом |
| `lite` | `memory_words` ≤ 5000 или `n` ≤ 40 | ты сам, без fan-out, + 1 верификатор |
| `full` | остальное | Workflow `kb-refresh.mjs`, писатель на файл; потолок 50 агентов и 300 агент-мин |

Оценка full: 2 агента на устаревший файл (писатель и до одного FIX) + 1 верификатор на 10
файлов + 1 верификатор выборки + 1 на каждые 40 кандидатов `lost`; × ~6 агент-мин. В один
Workflow идёт столько файлов, сколько влезает в `2·files + ⌈files/10⌉ ≤ maxAgents` (при
`maxAgents` 50 — не больше 23): первые по убыванию числа утверждений, остальные — следующим
прогоном.
Слова запроса («всё», «полностью») рекомендацию не повышают; явный выбор пользователя на
вопросе старта старше неё, оценка при этом показывается. Числа здесь и ниже — калибровка по
первым прогонам.

## 3. Вопрос старта — одна точка

Одно `AskUserQuestion`, до 4 вопросов, рекомендация первой; ненужные вопросы опускай. В тексте
вопроса — строки-предупреждения: `storage.memory.disk_richer_than_head` не пуст — «на диске
память богаче HEAD — правлю диск»; `storage.memory.modified` не пуст или
`storage.memory.head_vs_base.same: false` — «память на диске отличается от HEAD/базы — правлю
диск»; сводка `storage.memory.differs` (версии новее по дате, но не надмножество диска) —
только для сведения.

1. **База** — только если она взята из `origin/HEAD` (`repo.base.source: origin_head`):
   подтвердить `<ref>` / другая. «Другая» → повтори шаги 1–2 и покажи новую оценку строкой.
2. **Продолжение** — если `resume.present` (прогон не текущий) или
   `storage.memory.newer_versions` не пуст:
   - resume прерванного прогона (`resume.run`);
   - заново: сначала `lost` против `before` прерванного прогона, его кандидаты — строками
     отчёта, затем `snapshot --abandon --run <прерванный>`;
   - восстановить версию из `newer_versions` (надмножество диска: источник, `checked_max`,
     число файлов) — после снимка текущего диска.
3. **Глубина** — рекомендация с оценкой или «только отчёт». Для full вопрос звучит явно:
   «Workflow kb-refresh, до N агентов / ~M агент-мин — запускать? (да / lite / только отчёт)».
   «Да» — это opt-in из [`orchestration-patterns.md`](../reference/orchestration-patterns.md);
   без него не выше lite.
4. **Пакет** (multi-select):
   - архивация влитых фич вместе с удалением их служебного — только
     `features.items[].merge.state: merged`, с evidence (тикет, `merge.last_sha`,
     `merge.base_commits`); `unmerged` и `unknown` (в том числе `ticket_source: slug_ambiguous`)
     не предлагай, служебное невлитых фич не удаляется;
   - удаление целых файлов journal: `validate.budgets.journal.files[]` с `age_days` ≥ 180 и
     `has_open: false`;
   - коммит — только если текущая ветка — локальная ветка базы (для `origin/dev` — `dev`),
     HEAD не detached и правимые файлы tracked; иначе пункта нет, а в отчёте будет строка
     «правки на диске, ветка <X>; перенос в <база> — отдельным MR».

Пункты auto-memory — не отдельным вопросом: до вопроса собери чек-лист
`<snapshots_dir>/checklists/automemory-<run>.md` по `automemory.files` (`class`, `homes`,
предлагаемое действие), все пункты пустые, и назови путь в тексте вопроса. Применяется только
то, что пользователь отметил к моменту ответа. Ответ «только отчёт» — удали этот файл, его
пункты — в отчёт. Дальше до финала — без вопросов, кроме стопов шагов 5 и 7 и ошибки лимита.

Ответ о базе — и на шаге 0, и здесь, и база из `$ARGUMENTS` — записывается в `base:` (`metadata`
`memory/MEMORY.md`) первой записью после снимка.

## 4. Где работаем

- **Снимок** — перед первой записью и перед любым восстановлением, из дерева пользователя:
  `python3 <kb_scan> snapshot --run <run>`. При resume новый снимок не делается: `lost` идёт
  против `before` прерванного прогона. `snapshots_dir` и `path` бери из ответов
  `prepare`/`snapshot`, не вычисляй. «Только отчёт» не пишет ни в память, ни в снимки. Каталог
  прогона команда не удаляет никогда — ни при «только отчёт», ни при отмене.
- **Код базы** — в lite: `git worktree add --detach <snapshots_dir>/<run>/base <base-sha>`, ты и
  верификатор сверяете по нему, в worktree ничего не пишется. В full Workflow читает код
  через `git show <base-sha>:<путь>` и `git grep <base-sha>`, worktree не нужен.
- **Память** правится на месте, в дереве пользователя — tracked и untracked одинаково.

## 5. Проверка — модель работает только здесь

Единица — устаревший файл целиком: писатель сверяет с кодом базы **все** утверждения файла и
правит. `stale_anchors` — подсказка, где искать, а не граница сверки. Утверждения из
`unverified_anchors` (`branch_only`: якорь есть в HEAD или на диске, но не в базе) не
удаляются — строкой отчёта «не проверено: код только на ветке». `checked` писатели не ставят:
его ставит `stamp` после пост-проверки (шаг 7). Правила записи доходят до писателя текстом —
секция «Выжимка для писателя» скила `qtim:kb-format` дословно в промпте; `Skill` —
дополнительно, если он у писателя есть. Команды перепроверки, записанные в памяти, не
исполняет никто — ни ты, ни писатели, ни верификаторы: строкой отчёта «не исполнено, проверь
сам».

- **lite** — пишешь ты сам по скилу. Затем один верификатор — `Agent` с
  `subagent_type: Explore`: только утверждения, переписанные или удалённые по смыслу, против
  кода из worktree базы. FIX применяешь ты, повторной проверки нет, спорное — в отчёт.
- **full** — до старта положи `<snapshots_dir>/<run>/args.json`:
  `{base, baseSha, runId, maxAgents, writerRules, beforeDir, files:[{file, reason, claims}]}`,
  где `files` — `delta.files[]` со `stale: true` (`file` — путь `memory/…` от корня дерева,
  `claims` — их `stale_anchors`), `writerRules` — текст секции «Выжимка для писателя» из
  `SKILL.md` рядом со скриптом, `beforeDir` — `<path>/before` из ответа `snapshot`,
  `maxAgents` — потолок минус агенты вне Workflow (выборка, `lost`). Запуск —
  `Workflow({ scriptPath: '${CLAUDE_PLUGIN_ROOT}/workflows/kb-refresh.mjs', args })`; в
  standalone — `.claude/workflows/kb-refresh.mjs`. Писатель правит только свой файл и его
  journal-пару (путь — по скилу), без worktree-изоляции (отступление от
  [`orchestration-patterns.md`](../reference/orchestration-patterns.md)): файлы писателей не
  пересекаются, а `memory/` бывает untracked. Итог — `results[].state`:
  - `stamp: true` (`ok`, `no_change`, `fixed_unverified`) — в `stamp` шага 7; `fixed_unverified`
    ещё и строкой отчёта «исправлено без повторной проверки»;
  - `written_unverified`, `verifier_failed`, `writer_failed`, `incomplete`, `fix_skipped`,
    `fix_failed`, `batch_failed` — «не проверено» в отчёт с `summary`/`fixes`, по ним `lost`,
    без `stamp`;
  - `skipped` или `halted` не `null` — новых агентов не создавай (уже идущие писатели, до 10,
    доработают). До выхода — `lost` и `stamp --files` готовой части (`results[].stamp`) по
    шагу 7, прогон не закрывай. Продолжение — новый запуск Workflow по файлам, которые `delta`
    всё ещё считает устаревшими: проверенные уже со `stamp` и выпадут сами.
  - Сверка объёма: прямо перед запуском Workflow — копия `cp -R memory <path>/pre-wf-<N>`
    (N — номер запуска в прогоне); после — `diff -rq <path>/pre-wf-<N> memory`. Изменён файл
    вне `files[]` и их journal-пар → стоп: покажи список, восстановление — из этой копии по
    выбору пользователя (не из `before`: он откатил бы `base:` и работу прошлых запусков).
- **Выборка** — `delta.sample` (30 утверждений точек входа вне дельты): в lite её смотрит тот
  же верификатор, в full — отдельный `Explore` вне Workflow (учтён в оценке). ≥ 3 неверных в
  lite → стоп и предложение full с оценкой; в full — строки отчёта.

`open:` → `fixed:` — только если коммит-кандидат трогает путь якоря, он предок базы **и**
верификатор подтвердил по коду; по сообщению коммита — никогда.

## 6. Операции — детерминированно или по пакету старта

- **Сжатие точек входа до бюджета** (`validate.budgets.entry[].over`): эпизодика → journal со
  строкой-роутером; память под git — вместо переноса указатель `git show <sha>:<файл>` и итог
  в 1–3 строки.
- **Переякоривание** `path:line` → `path#Symbol` — по резолву из скила.
- **Архивация влитых фич из пакета** — статус `Archived` артефактам; что удаляется (в том числе
  служебное), что остаётся и как сжимается «История изменений» — § «Артефакты и статусы»
  [`feature-pipeline.md`](../reference/feature-pipeline.md).
- **Удаление файлов journal из пакета.** Живые `open:` из удаляемого файла сначала
  возвращаются в точку входа; пересказ journal запрещён.
- **auto-memory** — только при `automemory_copied: true` в ответе `snapshot`; применяются
  отмеченные пункты чек-листа; «удалить» — только после переноса фактов, пустого
  `lost --tree automemory` по файлу и подтверждения верификатора (на глубине `none`
  верификатора нет — удалений в auto-memory нет, только перенос и отчёт).
- **Charter, read-on-spawn агентов, `.claude/rules/`, `CLAUDE.md`, README** — только отчёт
  владельцам, в том числе когда прогон создал, удалил или переименовал файл памяти: строка
  «обнови read-on-spawn: <файл> → <роли>».

## 7. Пост-проверка

Всё — из дерева пользователя, где правилась память.

- `python3 <kb_scan> validate --base <база>` — новые замечания исправь до финала.
- `python3 <kb_scan> lost --snapshot <path>/before`, а если в пакете есть одобренные удаления —
  с `--expect-deleted <пути>` (один флаг на все пути, каталоги — префиксом, например
  `docs/features/<slug>/.work`; удалений нет — флаг опусти). `shrink_alarm: true` → стоп с
  `shrunk_files`, кроме файлов, которые шаг 6 сжимал штатно (сжатие до бюджета, «История
  изменений» при архивации) и по которым нет `candidates`/`open_lost`: их сжатие ожидаемо.
  Гейт роста по `growth.pct` (слова точек входа + journal): в lite рост > 10% — стоп с тремя
  файлами-лидерами роста; в full из состояния «`checked` не было» — строка отчёта. Все `open_lost` и `candidates` — верификатору
  (`Explore`, 1 на 40 кандидатов): перенесён / опровергнут кодом / потерян; потерянное
  восстанавливается из снимка. Правил auto-memory — то же с `--tree automemory`.
- `python3 <kb_scan> stamp --sha <base-sha> --files <проверенные файлы> --intact --snapshot
  <path>/before`: `--files` — файлы, сверенные целиком (в lite — всё, что ты сверил и
  верификатор не оспорил; в full — `results[]` со `stamp: true`); `--intact` — файлы без
  изменённых якорей, которые в этом прогоне не менялись (байт в байт с `before`): их сверка
  переносится на новую базу, и подсказка SessionStart гаснет. `skipped[]` с `reason`
  `unverified_anchors` или `changed_in_run` — `checked` остаётся старым, в отчёт как «не
  проверено».

## 8. Финал

- **Коммит** — только по «да» на вопросе старта: `git add -- <созданные прогоном пути>`, затем
  `git commit -m … -- <изменённые и созданные прогоном пути memory/ docs/features/>` (pathspec
  не захватывает чужие staged-изменения; без `add` новый файл роняет коммит целиком). Упал
  pre-commit-хук проекта — не обходи его, строка отчёта. Коммита нет — строка «правки на
  диске, ветка <X>; перенос в <база> — отдельным MR».
- **Закрытие прогона** — с коммитом и без, кроме прерванного full:
  `python3 <kb_scan> snapshot --after --run <run>` — из того же дерева, где начат прогон
  (иначе `run_foreign`). Он снимает маркер незавершённого прогона и лок; без него следующий
  `prepare` предложит resume.
- `git worktree remove <snapshots_dir>/<run>/base` — в lite, всегда: worktree чистый.
- **Отчёт** — по формату шага 5 [`intake-protocol.md`](../reference/intake-protocol.md), плюс:
  - до/после в словах и КБ; read-on-spawn по ролям (`validate.budgets.roles`);
  - «не проверено» — файлы шага 5, `skipped[]` из `stamp` и утверждения `branch_only`;
    «исправлено без повторной проверки»; «не исполнено» — команды из памяти;
  - «передать владельцам» — мёртвые и чужие контракты (`validate.consumers`), копии канона
    (`validate.canon_copies`), небезопасные команды в памяти (`validate.unsafe_commands`),
    неканонические файлы фич (`features.items[].extra`), прочее из шага 6;
  - auto-memory: `automemory.status`, превышение индекса (`automemory.index.over`),
    `automemory.index.broken_links`;
  - версии памяти на других ветках (`storage.memory.distinct_trees`) и в stash
    (`storage.memory.stashes`), `differs` — одной строкой каждое;
  - не больше 3 открытых вопросов.
