# PM-конвейер (feature pipeline) — контракты

> Generic reference плагина. Читает **только team-lead**. Субагенты читают правила из charter,
> не отсюда.
>
> **Разделение с [`/qtim:feature`](../commands/feature.md) — по времени жизни.** Здесь живёт то,
> что переживает сессию: схемы артефактов и семантика их статусов, handoff-контракт, правила
> grounded-оценки и нарезки. Порядок стадий, checkpoints, resume и спавн ролей — исполняемая
> часть, она в самой команде и здесь не дублируется. Charter-секция «PM-конвейер» (setup 4.1) —
> **производная** от этого файла: канон один, и он тут.

## Принцип

PM-трек документирует, dev-трек реализует. Артефакты — версионируемые файлы в
`docs/features/<slug>/` проекта. `memory/` хранит только решения и указатели, не содержимое
документов.

Конвейер двухтрековый — церемония пропорциональна риску, не классу задачи «фича». Полный трек
даёт пять артефактов, fast-path — один `feature-brief.md` (PRD-lite + work items с evidence +
план одной фазы + handoff). Критерий выбора трека и момент выбора — в
[`/qtim:feature`](../commands/feature.md); ось риска — в [`intake-protocol.md`](intake-protocol.md).

Точность описания важнее скорости: декомпозиция и оценка обязаны опираться на consult профильных
dev-ролей по реальному коду, а не на предположения product-роли. Consult read-only — dev-роли
в этих стадиях файлы не правят, их вывод это evidence для `product`; состав consult пропорционален
реально задетым слоям, а не вееру всех ролей.

## Артефакты и статусы

Канонический набор `docs/features/<slug>/` (slug — kebab-case от короткого имени фичи):

| Файл | Содержимое |
|---|---|
| `intake.md` | исходная хотелка + уточнения пользователя |
| `prd.md` | PRD: цели, сценарии, acceptance criteria |
| `decomposition.md` | work items с привязкой к слоям и файлам |
| `estimate.md` | сводка оценок S/M/L/XL по work items |
| `plan.md` | фазы реализации (ранние — с наибольшей неопределённостью), gates, ограничения пользователя, handoff |
| `feature-brief.md` | fast-path: PRD-lite + work items с evidence + план одной фазы + ограничения пользователя + handoff (заменяет prd/decomposition/estimate/plan) |

Шапка каждого файла: `Feature / Slug / Status: Draft | Approved | In Development | Done | Archived / Дата`;
в конце — секция «История изменений» (строка на ревизию, зафиксированное в реализации
отклонение, принятый риск или находку вне объёма). Для пишущих она append-only. Сжимает её
только [`/qtim:kb-refresh`](../commands/kb-refresh.md) при архивации: строки ревизий
схлопываются в одну «ревизии до <дата>: N записей» (под git — с добавкой «см. git»), строки
«Принятый риск», «Вне объёма», «Отклонение» не трогаются, удаления нет.

Служебные файлы фичи (consult-выводы, отчёты ревью фаз, логи прогонов, брифы проверок) — не
артефакты: где они лежат, по скилу `qtim:kb-format`.

**Семантика статусов** (переходы исполняют разные стороны — это контракт между треками):

| Статус | Что означает | Кто ставит |
|---|---|---|
| `Draft` | артефакт написан, пользователем не утверждён | PM-трек при создании |
| `Approved` | пользователь утвердил на checkpoint'е; стадия закрыта | PM-трек после подтверждения |
| `In Development` | dev-трек взял фичу в работу | тот, кто реализует |
| `Done` | фазы плана выполнены, verification gates зелёные | тот, кто реализует (team-lead по завершении эпика) |
| `Archived` | фича влита в базовую ветку; служебное удалено, фича закрыта | только `/qtim:kb-refresh` по признаку «влита» |

**Архивация:** итог фичи строкой к её указателю в `memory/decisions.md`; удаляются `.work/`,
dot-файлы и `consult/`; `intake`/`prd`/`decomposition`/`estimate`/`plan`/`feature-brief`
остаются — это reference class оценок и вход retro.

**Признак завершённости конвейера — не статус, а указатель.** У стадии Handoff собственного
артефакта нет, поэтому плановый документ в `Approved` и выше **без** строки-указателя на фичу
в `memory/decisions.md` означает обрыв на Handoff, а не закрытый конвейер. Механика возобновления
по этому признаку — в [`/qtim:feature`](../commands/feature.md).

**Правило dev-consult (декомпозиция и оценка):** `architect` смотрит слои, data flow и инварианты
(его режим CONSULT); `db` / `front` / `tester` — каждый свой слой: затронутые файлы,
интеграционные точки, похожие существующие фичи, риски. `explorer` — для широкого read-heavy
поиска. Ограничения consult (read-only, состав ∝ задетым слоям) — в «Принципе» выше.

**Правило нарезки (work items и фазы плана):** work item и фаза плана — вертикальный срез: узкий, но
полный путь через задетые слои (схема → API → UI → тесты), демонстрируемый или проверяемый
сам по себе; не горизонтальный этап одного слоя («вся БД, потом весь UI»). Исключение —
широкий механический рефактор (rename / retype с blast radius на всю кодовую базу): он в
вертикальный срез не встаёт — планируй его как **expand–contract**: добавить новую форму
рядом со старой (ничего не ломается) → мигрировать call sites пачками по слою/каталогу
(каждая пачка — отдельный work item, гейты зелёные между пачками) → удалить старую форму
последним item'ом, когда вызовов не осталось.

## Правила grounded-оценки

- Шкала только относительная: **S / M / L / XL** + confidence (high / medium / low) + риск-факторы.
  Часы и дни не выдумывать.
- XL означает «work item нужно разрезать», а не «очень долго».
- Размер work item даёт профильная dev-роль — владелец слоя, не product.
- Каждая оценка обязана ссылаться на evidence: конкретные файлы, покрытие тестами, число
  интеграционных точек, похожие прошлые фичи (реестр решений и фич `memory/decisions.md`, git log) как reference class.
- Оценка без evidence не принимается в `estimate.md`.

## Handoff contract

- `plan.md` заканчивается секцией `## Handoff` с готовой формулировкой задачи для
  [`/qtim:team-up`](../commands/team-up.md) (многофазные фичи) или
  [`/qtim:team-lazy`](../commands/team-lazy.md) (S/M в одну фазу).
- Dev-команда читает `plan.md` (scope, фазы, gates) и `prd.md` (acceptance criteria) как источник
  требований.
- Кто реализует — обновляет Status артефактов (`In Development` при старте, `Done` после gates)
  и фиксирует отклонения от плана с обоснованием и всплывшие edge cases строкой в «Истории
  изменений» `plan.md` — это вход для [`/qtim:team-retro`](../commands/team-retro.md) и resume
  многофазных фич.
- В реестр решений и фич (`memory/decisions.md`) добавляется одна строка-указатель на утверждённую фичу — **последней операцией стадии 6**, после того как секция `## Handoff` сформирована и сообщена: по этой строке resume отличает завершённый конвейер от оборвавшегося.

## Anti-patterns

> Нарушения **контрактов** — что попадает в артефакты и на чём стоят оценки. Ошибки ведения
> конвейера (пропуск checkpoint, выбор трека не по риску, перезапуск при существующем slug) —
> в [`/qtim:feature`](../commands/feature.md), там же где сама механика.

- Оценки и декомпозиция без consult профильных ролей по реальному коду.
- `product` пишет production code, SQL или тесты.
- Куски кода / SQL внутри артефактов — артефакты держат контракты, инварианты и acceptance
  criteria, не диффы.
- PRD и решения только в чате или `memory/` вместо `docs/features/`.
- Дублирование содержимого артефактов в `memory/` вместо указателей.
- Молчаливое отклонение от `plan.md` в реализации — без строки в «Истории изменений».
