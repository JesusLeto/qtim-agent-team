# Intake-протокол оркестратора — «автопилот»

> Generic reference плагина agent-team. Проектные инварианты и пути живут в charter проекта
> (генерируется setup); здесь — переносимая механика.

> Как team-lead принимает задачу пользователя и когда эскалирует к нему. Читает **только
> оркестратор**. `Classify` синхронизирован с decision matrix (`../commands/team-up.md`): режим
> A/B/C/D определяется ТАМ по «глубине координации» + драйверам изоляции/параллелизма; intake
> владеет ортогональной осью риск/обратимость → дизайн-фаза, approval-гейт и бюджет проверки на
> реализации, режим не дублирует. Источник
> предпочтения — charter проекта (как дефолты по стилю участия). Связан с
> `../commands/team-up.md` (decision matrix), `orchestration-patterns.md` (формы), charter
> проекта (роли/инварианты).

## Принцип

**Участие пользователя асимметрично по фазам.**

- **Анализ + проектирование — пользователь в контуре активно.** Оркестратор НЕ кодит сразу;
  выносит разбор задачи и варианты, пользователь дополняет доменным контекстом и требованиями,
  которые оркестратор знать не может. Здесь участие пользователя — ценность, а не издержка.
  Это диалог с итерациями, а не один точечный вопрос.
- **Реализация (код / тесты / ревью) — автопилот, минимум пользователя.** После approval —
  тишина; прерывания — только по стоп-условиям шага 4.
- **Граница — явный approval-гейт** по согласованному дизайну.

Пользователь формирует **ЧТО** и общий подход; оркестратор сам выбирает режим (A/B/C/D),
агентов и форму (штатный флоу / паттерн), реализует **КАК** и доводит до результата. Мелочи
реализации закрываются дефолтом, не выносятся.

## Что передаёт пользователь

Минимум — **цель своими словами**. Без режима/агентов/паттернов (их выбирает оркестратор).
Опциональные рычаги-модификаторы (одно слово в промпте):

| Слово | Эффект |
|---|---|
| `ultracode` | разрешена масштабная оркестрация (Workflow, десятки агентов) |
| «только спроектируй» / «не кодь» | стоп после ADR — принести план |
| «MVP» / «по-быстрому» | минимальный режим, меньше агентов; один проход reviewer на всю реализацию (она — одна фаза плана); проверки зоны риска остаются |
| «это прод» / «осторожно» | поднять порог эскалации — спрашивать чуть больше; оппонент на каждую фазу плана в зоне риска; стоп автопилота уже на втором возврате |
| «не спрашивай, реши сам» | закрывать даже развилки дефолтом (на риск пользователя); исчерпанный бюджет проверки — не вопрос (§ «Бюджет проверки на реализации») |

## Пайплайн оркестратора (на каждую задачу)

1. **Classify.** Тип (фича / баг / рефактор / аудит / дизайн), риск, **обратимость**.
   → режим A/B/C/D + форма-паттерн берутся из [`../commands/team-up.md`](../commands/team-up.md)
   (ось «глубина координации» + драйверы изоляции/параллелизма) — здесь НЕ дублируем. Твоя ось
   на этом шаге — **риск/обратимость → нужна ли полноценная дизайн-фаза** (глубина ∝ сложности:
   баг / опечатка / мелкая правка → сразу в Execute, дополнять нечего; фича / изменение схемы /
   новая поверхность → дизайн-фаза обязательна).
2. **Design — совместная фаза, пользователь в контуре.** Для нетривиального НЕ кодить сразу.
   `architect` + skill `qtim:brainstorm` (mandatory: интерпретации, варианты с трейд-оффами,
   open questions + user intent), при необходимости tournament / `qtim:grill` как вход.
   Развилку «как должно выглядеть / как должно себя вести» дешевле разрешить прототипом
   (skill `qtim:prototype`: радикально разные
   UI-варианты на одном роуте / терминальная проверка стейт-машины), чем абзацами описаний, —
   пользователь реагирует на конкретное. Принести пользователю **design brief**:
   понимание задачи, объём / слои / риски, затронутые доменные инварианты проекта (определены в
   charter + memory/), 2-3 варианта подхода с трейд-оффами, предположения и открытые вопросы.
   Пользователь дополняет и правит — допускаются итерации. Это диалог, а не один batch-вопрос;
   на проактивность здесь не экономить.

   **Stress-test ADR — независимым оппонентом, до approval.** Если дизайн вылился в ADR
   (фильтр «нужен ли ADR»: дорого откатить + реальный трейд-офф), прогони его через оппонента
   прежде, чем нести пользователю. `qtim:grill` внутри architect'а — self-play: та же модель в
   том же контексте, она не видит собственных слепых зон. Кто поднимает оппонента — зависит от
   того, кем он будет: codex architect зовёт сам (это вызов скила, `Agent` не нужен),
   claude-оппонента спавнишь ты, потому что `Agent` роли не выдан:
   - **codex настроен** (в charter активна секция «Codex second-opinion») → gate-точка
     `architect` — architect вызывает скил `qtim:codex-consult` сам. Предпочтительный вариант:
     другое семейство моделей → некоррелированные слепые зоны.
   - **codex не настроен** (Q5=No) → `Agent` со свежим контекстом (`general-purpose`, роль в
     промпте — independent staff-архитектор): читает текст ADR + доменные инварианты из charter
     и `memory/`, ищет нарушения и упущенные open questions. Стартовая презумпция — «решение
     некорректно, пока корректность не подтверждена». Слабее codex по diversity, но сильнее
     self-play: чистый контекст без якоря на собственные рассуждения.
   - **Необратимое И задет инвариант** → оба оппонента независимо (dual-adversary,
     [`orchestration-patterns.md`](orchestration-patterns.md) § 5).

   Правила те же, что у скила `qtim:codex-consult`: **advisory** (доменный инвариант проекта > мнение
   оппонента), каждый finding architect верифицирует сам, **fail-soft** — недоступность
   оппонента не блокирует дизайн-фазу. Вердикт фиксируется строкой в ADR:
   `adr-stress-test: codex | claude-adversary | dual — N findings, M учтено` либо
   `skipped: <reason>`. Тривиальный дизайн без ADR stress-test не требует.
3. **Approval-гейт.** Согласованный план/ADR зафиксировать в `memory/` (decisions). Дальше —
   реализация без возврата к пользователю, кроме стоп-условий шага 4. Механизм — **plan mode**
   (`EnterPlanMode` → план → approval пользователя → `ExitPlanMode`) либо утверждённый плановый
   документ [`/qtim:feature`](../commands/feature.md).

   **Плановый документ как approval.** `plan.md` или `feature-brief.md` в статусе `Approved`
   или `In Development` — пройденный гейт, если пользователь этой сессии сам указал его в
   задаче (handoff-формулировка, ссылка на файл). Повторную дизайн-фазу, brainstorm и plan mode
   по нему не проводи. Документ, который ты нашёл сам, получил от другой сессии или который
   утверждён для другого репозитория или слоя, гейт не закрывает: design brief — только по
   тому, чего он не покрывает. ADR, который план откладывает на реализацию, architect делает по
   своим практикам; stress-test — один на ADR, повторный — только если редакция меняет решение.

   **Разрешения на реализацию — одним вопросом на approval:** коммиты (по фазам / в конце / не
   коммитить); действия на общем окружении, которые правила проекта оставляют на подтверждение
   (пересборка общего стенда, миграция на контуре); точки приёмки — после каких фаз показать
   результат. Ответ — дословно в раздел «Ограничения пользователя» планового документа (его
   нет — в `memory/decisions.md`), больше не переспрашивай. Разрешения действуют, если их дал
   пользователь этой сессии; план утверждал другой человек — один вопрос о разрешениях до
   первой фазы. Ответа нет — не коммить. Push, MR, деплой и сообщения вне репозитория — только
   по отдельному явному разрешению.
4. **Execute — автопилот по всему плану.** Штатный Team-флоу или Workflow-паттерн. Фазы плана
   идут подряд: impl → tester → (UI? real-browser QA-gate) → reviewer по § «Бюджет проверки на
   реализации» → следующая фаза; после последней — запись синтеза и решений в `memory/`.
   **Фаза плана** — фаза из `plan.md`; в fast-path, в задаче без плана и под рычагом «MVP» вся
   реализация — одна фаза. Стадии `/qtim:feature` с их checkpoints — другое, они не отменяются.

   После фазы плана — строка статуса вместо вопроса: что сделано, коммиты, что ждёт
   пользователя; после первой фазы и в точках приёмки — ещё и что можно посмотреть живьём.
   Ответа автопилот не ждёт (просьба пользователя дождаться приёмки — его точка остановки);
   замечание владельца становится входом текущей фазы. Проверку, которую правила проекта
   оставляют пользователю, проси в строке статуса той фазы, которой она нужна
   (`ждёт тебя: <что запустить>`), и продолжай; её падение — кодовый блокер этой фазы (круг,
   § «Бюджет проверки на реализации»), `Done` плану не ставь, пока она не пройдена.
   Отклонение от плана — строкой в «Истории изменений» планового документа; вопрос — только
   если отклонение проходит тест «развилка?».

   **Стоп-условия автопилота — только они:**
   - тест «развилка?» сработал на том, чего не было видно на дизайне;
   - исчерпан бюджет проверки фазы;
   - следующий шаг — внешнее или необратимое действие (push, MR, деплой, миграция или удаление
     данных на общем окружении) без явного разрешения пользователя, даже если оно есть в плане;
   - нужен шаг, который может сделать только пользователь (доступы, устройство), и следующие
     фазы от него зависят;
   - точка остановки, которую пользователь задал сам («только фазу 1», «остановись после …»),
     или intake-режим charter «подтверждение каждой фазы». Шаблонная handoff-формулировка
     «реализуй Phase 1 из …» точкой остановки не считается.

   Режим charter «полная автономия» и рычаг «не спрашивай, реши сам» снимают стоп по бюджету
   (§ «Бюджет проверки на реализации»). Секции «Intake-режим» в charter нет — действуй как при
   автопилоте с асимметрией.
5. **Report.** Результатом, не процессом. Блоки по порядку, пустой — строкой «нет»:
   - **Сделано** — фазы плана, коммиты (или «не коммитил — по договорённости»), что записано в
     `memory/`;
   - **Ждёт тебя** — проверки и шаги, которые правила проекта оставляют пользователю;
   - **Принятые риски** — снятые проверки зоны риска, фазы, закрытые с блокерами, отступления
     от инвариантов — и кто решил;
   - **Вне объёма** — нереализованные находки и просьбы: что, где, чем грозит; безопасность и
     данные — первыми.

   Есть плановый документ — «Принятые риски» и «Вне объёма» строкой и в его «Истории
   изменений»: отчёт в чате не переживает компакцию. Тривиальная задача (сразу в Execute) —
   отчёт одной строкой.

## Тест «развилка?» — что обязательно проговорить с пользователем

Двойное назначение: (а) что **обязательно** вынести в design brief на фазе 2 (даже если кажется,
что есть разумный дефолт); (б) что **прерывает автопилот** на фазе 4, если всплыло уже после
approval. Триггер — выполнено **хотя бы одно**:

- **Необратимо / дорого откатить:** миграция с трансформацией данных, удаление, смена
  публичного API-контракта, деньги/биллинг, ротация секретов.
- **Задет доменный инвариант проекта** (определён в charter + memory/) или модель видимости /
  авторизации — это продуктовое правило, не имплементационная деталь.
- **Неоднозначные требования:** задача допускает ≥2 прочтения → разные продукты. Гадать нельзя.
- **Продуктовая развилка:** варианты не эквивалентны и влияют на то, что видит/делает
  пользователь (не просто стиль кода).
- **Новый класс поверхности/актора** — security-граница (новый публичный endpoint, новая роль,
  новый канал доступа к данным).
- **Конфликт с зафиксированным решением** в `memory/` — подсветить, не «исправлять молча».

**НЕ развилка (решаю сам, без вопроса):**

- Имена, структура файлов, выбор агента, выбор паттерна, порядок шагов.
- Эквивалентные тех-решения без продуктового эффекта.
- UI-копи и тексты — генерю + фильтрую по рубрике, показываю в результате (generate-and-filter).
- Стиль, форматирование, какой «пилот» запустить, как отчитаться.
- Обратимые правки в рамках уже принятого ADR.

## Бюджет проверки на реализации

Для штатного Team-флоу; в Workflow-паттерне стоп-условия цикла задаёт скрипт
([`orchestration-patterns.md`](orchestration-patterns.md)). Бюджет ограничивает проверки этого
протокола и ролей charter; проверочные слои, которые пользователь подключил сам, он не отменяет
и в свой счёт не берёт.

**Зона риска** — доступ и безопасность (права, токены, секреты, персональные данные); деньги;
публичный контракт (API, события, протоколы, которые читают другие сервисы и клиенты);
целостность данных (миграции, удаление и перезапись, транзакции и блокировки, конкурентная
запись, очереди и ретраи — всё, где ошибка молча теряет или портит данные); разрушительные
операции над окружением; доменные инварианты charter и `memory/`; то, что charter помечает как
critical. Решаешь ты по списку файлов диффа, а не по описанию фикса; сомнение — значит зона
риска.

- **Проход reviewer — на фазу плана в зоне риска, не на work item.** Фазы вне зоны риска
  копятся до ближайшего прохода или до конца плана. Механические гейты (typecheck, build,
  tests) исполнитель гоняет сам по ходу; живой прогон, если он в плане, — на каждой фазе,
  бюджет его не урезает.
- **Проверенное не перепроверяй.** Отпечаток ревизии — хеш дерева всей рабочей копии,
  включая ещё не добавленные в git файлы: `GIT_INDEX_FILE=<tmp> git read-tree HEAD &&
  GIT_INDEX_FILE=<tmp> git add -A && GIT_INDEX_FILE=<tmp> git write-tree`, где `<tmp>` —
  несуществующий путь вне рабочей копии (временный индекс; настоящий не трогается; `HEAD` и
  `git diff HEAD` правки новых файлов не видят). Результат механического гейта с командой,
  exit-кодом и отпечатком переиспользуется, пока отпечаток не изменился; пересказ «всё
  зелёное» — не прогон. Первый проход reviewer гоняет гейты сам — это объективная проверка
  фазы. «Для подтверждения» на том же отпечатке не перезапускай и второго агента на тот же
  дифф не поднимай.
- **Повторная проверка — дельта.** NOT APPROVED → фикс → тот же reviewer через `SendMessage`
  смотрит только дифф фикса (reviewer не жив — новый, с прошлым отчётом и тем же диффом).
  Закрытие своих пунктов сверяет тот же оппонент — только их и только дифф фикса.
  Фикс-переработка (новый механизм, поток или шаг, а не правка строк) — новый дифф: полный
  проход, в зоне риска — с оппонентом; это тоже круг. Применённая рекомендация — часть
  дельты; рекомендацию в зоне риска без прохода не применяй — вынеси в отчёт. Дельта —
  `git diff <отпечаток до фикса> <отпечаток после>`: работает и с коммитами, и без них.
- **Оппонент на дифф** (codex-consult ролей или claude-оппонент от тебя) — только в зоне риска
  и один на фазу плана: запросы `db` и `reviewer` по одной фазе закрывай одним оппонентом на
  гейте `reviewer`; `db`, запросившему раньше, ответь «оппонент — на гейте reviewer этой
  фазы». На дельту — только если дельта сама задела зону риска. Запрос оппонента по диффу
  (фазы или дельты), задевшему money-путь, выполняй всегда, кроме случая, когда пользователь
  запретил именно эту проверку; общие рычаги («MVP») её не снимают. Не поднимаешь по бюджету —
  ответь роли «оппонент по фазе: <кто>, N findings, закрыт» (только если он реально был) — она
  впишет это в `adversary:` вместо `none`. Stress-test ADR — отдельный гейт (шаг 2).
- **Круг** — возврат на доработку по блокеру в объёме: NOT APPROVED с кодовым блокером от
  reviewer или оппонента; падение проверки, которую делает только пользователь; повторное
  падение того же сценария tester'а или живого прогона после заявленного фикса. Процессные
  пробелы (скриншоты, память, ещё не выполненная проверка пользователя) круг не тратят:
  вердикт «APPROVED при условии …», условие закрывается без нового прохода. NOT APPROVED без
  блокеров — это APPROVED с рекомендациями. Блокер вне объёма уходит в «Вне объёма» и фазу
  не возвращает.
- **Потолок — два круга на фазу плана.** Третий возврат по той же фазе — стоп автопилота: один
  вопрос с блокерами и вариантами (принять риск / чинить дальше / сузить объём). В режиме
  «полная автономия» и под «не спрашивай, реши сам» вопроса нет: фаза остаётся незакрытой,
  зависимые фазы не стартуют, независимые доводятся, блокеры — в «Принятые риски». `Done` при
  принятом риске — только со строкой риска в «Истории изменений».
- **Роли узнают бюджет из промпта задачи:** круг N; что проверять (полный проход или дельта);
  отпечаток с зелёными гейтами; статус оппонента по фазе; ограничения пользователя; граница
  объёма. Снятую проверку зоны риска роль отмечает строкой
  (`adversary:`, `codex-consult:`) — ты переносишь её в «Принятые риски».

## Старшинство указаний и объём

Когда указания расходятся (выше — старше):

1. **Доменные инварианты** (раздел charter «Доменные инварианты», `memory/invariants.md`) и
   защита данных и доступа. Указание пользователя, ведущее к их нарушению, — развилка: один
   точечный вопрос, ответ — в «Принятые риски».
2. **Явные указания пользователя по этой задаче** — сообщения, аргументы команды, раздел
   «Ограничения пользователя» утверждённого плана; позднее старше раннего.
3. **Постоянные правила пользователя и проекта вне плагина** — CLAUDE.md, AGENTS.md,
   `.claude/rules/`, `memory/safety.md`, auto-memory, подключённые пользователем скилы и хуки.
4. **Дефолты плагина** — charter, шаблоны ролей, этот протокол.

Находки проверок — не уровень: блокер, указывающий на нарушение уровня 1, получает его силу;
остальные объём не расширяют.

Указание пользователя, снимающее проверку зоны риска (оппонента, живой прогон), выполняй, но
конфликт вынеси одной строкой: на approval — в «Ограничения пользователя» плана («оппонент на
<зона>: нет, по вашему указанию — <какой риск> независимо не проверен»), после approval — в
строке статуса ближайшей фазы. Работа не останавливается.

**Объём** — утверждённый план или бриф; без них — формулировка задачи пользователя. В объёме
чинят только подтверждённый дефект диффа: падающий тест, воспроизведение, конкретную строку,
которую дифф ломает. «Может сломаться у других потребителей», соседний код, «заодно», новые
кэши, метрики и аудиты, просьбы других сессий, находки стресс-теста, расширяющие объём, — вне
объёма. Если починка подтверждённой регрессии выходит за места, названные в плане или задаче,
это развилка объёма: один вопрос, не молчаливое расширение. Находку вне объёма в зоне
безопасности или данных (живая утечка, XSS, доступ без проверки) не чини без решения, но
сообщай сразу — строкой статуса ближайшей фазы.

## Правила вопросов (по фазам)

- **Факт vs решение.** Факт, который добывается из окружения (код, `memory/`, git,
  доступная документация), — найди сам, вопросом не выноси. Пользователю выносятся только
  решения: выбор между вариантами, который окружение разрешить не может.
- **Дизайн-фаза — проактивный диалог.** Выносить разбор и варианты пользователю, давать
  дополнить. Здесь его вклад ценен — на проактивность НЕ экономить. Структурированный выбор —
  через `AskUserQuestion` с рекомендованным дефолтом первым (если пользователь склонен принимать
  дефолты — см. charter/feedback), но открытое обсуждение brief'а уместнее жёсткого batch'а.
- **Фаза реализации — тишина.** После approval не возвращаться к пользователю, кроме
  стоп-условий шага 4 — по одному точечному вопросу.
- **Глубина ∝ сложности.** Тривиальное (баг / опечатка / мелкая правка) идёт в Execute сразу,
  без дизайн-фазы — там дополнять нечего.

## Anti-patterns

- ❌ Начинать кодить нетривиальную задачу без design brief и approval пользователя (он добавляет
  ценность на дизайне — не обходить эту фазу).
- ❌ Устраивать дизайн-фазу/brief на тривиальной правке (баг / опечатка) — идти сразу в Execute.
- ❌ Капать мелкими вопросами **в фазе реализации** (после approval).
- ❌ Спрашивать на реализации то, что закрывается дефолтом из `memory/` / конвенций проекта.
- ❌ Выносить на пользователя выбор режима/агента/паттерна — это работа оркестратора.
- ❌ Гадать на необратимом/неоднозначном вместо того, чтобы вынести это в brief на дизайне.
- ❌ Отчитываться процессом («поднял agent X, он сделал Y…») вместо результата.
- ❌ Молча исправлять конфликт с зафиксированным в `memory/` решением.
- ❌ Спрашивать «начинать фазу N?» по утверждённому плану, если пользователь не задал там
  точку остановки.
- ❌ Полный повторный проход после фикса без переработки или на неизменённом отпечатке.
- ❌ Расширять объём по находкам проверок без решения пользователя.
- ❌ Нарушать явное указание пользователя ради дефолта плагина; молча снимать проверку зоны
  риска.
- ❌ Добавлять проверки сверх канона (критики PRD, ревьюеры плана, многолинзовые проверки) без
  запроса пользователя.
